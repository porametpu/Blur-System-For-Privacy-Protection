# ผลตรวจเนื้อหาและแผนภาพก่อนแก้ไข

ตรวจวันที่ 28 ตุลาคม 2569 จากไฟล์รายงานปัจจุบันและภาพต้นฉบับใน Template_Project_2026
รอบนี้แก้เฉพาะปกนอกและปกใน ส่วนเนื้อหาบท 1–5 และภาพต้นฉบับคงเดิม
การตรวจนี้เป็นการตรวจเอกสารและความสอดคล้องภายในเล่ม ยังไม่ได้ยืนยันพฤติกรรมจากการรันระบบหรือเทียบกับโค้ดทุกจุด
เลขด้านล่างเป็นเลขภาพในรายงาน จึงไม่เปลี่ยนเมื่อเพิ่มหน้าปก

## ประเด็นที่พบชัดเจนและควรแก้ก่อน

| จุดตรวจ | สิ่งที่พบ | แนวทางแก้ในรอบถัดไป |
|---|---|---|
| ภาพ 12 Activity: Upload | ทางเลือกวิดีโอ/รูปภาพไปรวมที่แถบทึบแบบ Join ทั้งที่เลือกทำเพียงทางเดียว | ใช้ Merge รูปข้าวหลามตัดแทน Join ซึ่งใช้รอหลายกระแสที่ทำพร้อมกัน |
| ภาพ 12 Activity: Upload | ทางสำเร็จจาก Tools Selection ไหลต่อไป “รับแจ้งเตือน” ที่รับเส้นจากทางผิดพลาดด้วย และมี “แจ้งข้อผิดพลาด” ซ้ำสองจุด | แยกเส้นทางสำเร็จและผิดพลาด แล้ว Merge ก่อนจบ หรือให้ทางผิดพลาดย้อนกลับเลือกไฟล์ |
| ภาพ 13 Activity: Auto-Blur | ทาง “ไม่พอใจ” ไป “กลับไปปรับค่าใหม่” แล้วไหลลงจุดจบทันที ไม่ได้ย้อนปรับ/สร้าง Preview ใหม่ | ต่อเส้นกลับไปตั้งค่าและสร้างตัวอย่าง จากนั้นประเมินความพอใจใหม่ |
| ภาพ 17 Activity: Preview & Export | ทาง “ไม่พอใจ” ไป “กลับไปปรับการตั้งค่า” แต่ลูกศรกลับเข้าสู่ “กดปุ่ม Export” | ย้อนกลับขั้นตอนปรับค่าและสร้าง Preview ก่อนยืนยัน Export |
| ภาพ 13–15 | ใช้รูปหกเหลี่ยม/กรอบหลายเหลี่ยมแทน Decision และมีการนำหน้าตากรอบคล้าย combined fragment มาใช้แทนวงรอบใน Activity | กำหนดรูปแบบ UML ให้สม่ำเสมอ ใช้ Decision/Merge รูปข้าวหลามตัด พร้อม guard เช่น [ใช่]/[ไม่ใช่] และเส้นย้อนกลับชัดเจน |
| ภาพ 16 Activity: Image Redaction | มีแถบ Fork หลังปุ่ม Manual Control แต่ต่อออกเพียงเส้นเดียว และทางไม่เพิ่ม Zone ไม่ได้แยกออกจาก Decision อย่างชัดเจน | ตัดแถบทึบที่ไม่มีการแตกกระแส และวาดทาง [เพิ่ม]/[ไม่เพิ่ม] แยกกันก่อน Merge |
| ภาพ 14 Activity: Detect & Select | ลูกศรจากกดปุ่มไปเริ่ม Detection ซ้ำสองเส้น และทาง “ไม่ดู Timeline” ยังไปกิจกรรม “ดูข้อมูล Timeline” | ลบลูกศรซ้ำและให้ทางไม่ดูข้ามกิจกรรมนั้นไปเลือกบุคคล |
| ภาพ 13, 14, 18–22 | ระบุ YOLOv8 ในภาพ แต่บท 2 และตารางผลเปรียบเทียบระบุ YOLO26/YOLOv26n | ยืนยันชื่อโมเดลของแต่ละโหมด แล้วใช้ชื่อให้ตรงกัน อาจใช้คำกลาง YOLO Face Detector ในภาพรวม หากระบบเลือกหลายรุ่นได้ |
| ภาพ 18 Use Case | ไม่มี Livestream และการเลือกโมเดล ทั้งที่ FR-10/FR-11 และบท 4 อธิบายว่ามีแล้ว | เพิ่มความสามารถตามขอบเขตจริง หรือระบุชัดว่าภาพนี้ครอบคลุมเฉพาะงานไฟล์ |
| ภาพ 17 Activity: Export | วาดการอัปโหลด Cloudinary เป็นขั้นตอนบังคับเสมอ แต่ข้อความรายงานระบุว่าทำได้เมื่อมีข้อมูลรับรอง | แสดงเงื่อนไขเปิดใช้ Cloudinary และทางส่งไฟล์ในระบบเมื่อไม่ได้ใช้บริการนี้ |
| ภาพ 12, 19 และคำอธิบายการ Upload | ระบุว่าตรวจประเภทและขนาดไฟล์ แต่บท 5 ระบุว่ามีค่ากำหนดขนาดสูงสุดแต่ยังไม่บังคับก่อนบันทึก | ยืนยันว่าตรวจที่ส่วนใดและตรวจอะไรจริง แล้วปรับข้อความ/ภาพให้ตรงกัน |

## ประเด็นด้าน Sequence Diagram ที่ควรทบทวน

- ภาพ 11 และ 19–25 ใช้ชื่อ System Sequence Diagram แต่แสดง Frontend, Backend, โมเดล และฐานข้อมูลภายในระบบ ควรตกลงกับอาจารย์ว่าจะใช้ SSD ในระดับระบบเป็นกล่องเดียว หรือใช้ Sequence Diagram ระดับออกแบบ ชื่อและรายละเอียดควรสอดคล้องกับระดับที่เลือก เรื่องนี้เป็นประเด็นการกำหนดระดับแบบจำลอง ไม่ใช่ข้อสรุปว่าแผนภาพที่มีหลาย lifeline ผิด UML ทั้งหมด
- ภาพ 19–25 วาดกล่องชื่อผู้เข้าร่วม/Actor ซ้ำท้าย lifeline ทำให้สับสนกับการสร้างผู้เข้าร่วมใหม่ ควรคงชื่อไว้ด้านบนและใช้เส้น lifeline ต่อเนื่อง การจบภาพไม่จำเป็นต้องมีเครื่องหมายทำลายวัตถุหากวัตถุยังมีอยู่
- ภาพ 20–21 แสดงงานตรวจจับก่อนเข้าสู่วงรอบ Polling แต่ข้อความรายงานอธิบาย Background Task ควรแสดงการตอบรับเริ่มงานก่อน จากนั้นแยกงานเบื้องหลังกับการถามสถานะ และกำหนดเงื่อนไขจบวงรอบ เช่น [ยังไม่เสร็จ] ไม่ให้ตีความว่าต้องรอประมวลผลเสร็จก่อนเริ่มถามสถานะ
- ภาพ 21 จบที่ถามสถานะโดยไม่แสดงการอ่านผลและแสดง Face Map ขณะที่ Activity ของฟังก์ชันเดียวกันไปถึงเลือกบุคคล ควรกำหนดขอบเขตของภาพแต่ละชนิดให้ตรงกันหรือระบุว่าทำงานต่อที่ภาพใด
- ในขั้นตอน Export ควรมีกรณีเรนเดอร์/อัปโหลดไม่สำเร็จและเส้นทางลองใหม่ตามที่ระบบรองรับ ไม่เติมพฤติกรรมที่ระบบยังไม่มี
- การมี activation bar หรือการไม่วาด return message ทุกข้อความ ไม่ใช่เหตุผลเพียงพอที่จะตัดสินว่าภาพผิด ควรตรวจลำดับเหตุการณ์ เจ้าของงาน ชนิดข้อความ และ guard เป็นหลัก

## แผนภาพ Livestream ที่จัดวางใหม่ในรอบก่อน

- ภาพ 8 เป็นผังแบ่งหน้าที่และเส้นทางข้อมูล อ่านได้ครบแล้ว แต่หากต้องการใช้เป็น UML Activity แบบเป็นทางการ ควรเพิ่ม Initial, เงื่อนไขประมวลผลซ้ำ และเส้นทางหยุดสตรีมให้ชัดเจน
- ภาพ 10 ใช้กล่องกระบวนการเป็นจุดเริ่มต้นและไม่มีทางหยุดสตรีม หากชื่อเป็น Activity Diagram ควรปรับสัญลักษณ์และเงื่อนไขให้ครบ
- ภาพ 11 ใช้ลูกศรโค้งพร้อมข้อความ “วนรอบเฟรมถัดไป” เป็นคำบอกวงรอบ ควรใช้ combined fragment แบบ loop และ guard ใน Sequence Diagram
- การปรับในรอบก่อนเน้นปัญหาภาพถูกตัดและลูกศรทับข้อความ ยังไม่ถือว่าได้แก้ความหมาย UML ของทุกภาพครบแล้ว

## รายละเอียดอื่นในเนื้อหาที่ต้องยืนยันก่อนแก้

1. FR-07 ระบุ Manual Control ว่าอยู่ระหว่างพัฒนา แต่ตารางความก้าวหน้าและบท 5 อธิบายว่ามีในระดับต้นแบบ ควรแยกสถานะ “พัฒนาแล้ว” “ทดสอบแล้ว” และ “ยังไม่เสร็จ” ให้เข้าใจตรงกัน
2. ตารางผลเปรียบเทียบที่ระบุ Ours มี AP และ Latency แต่ยังขาดรายละเอียดชุดทดสอบ รุ่น/น้ำหนักโมเดล ฮาร์ดแวร์ วิธีจับเวลา และหลักฐานผลลัพธ์ ควรเตรียมข้อมูลเหล่านี้ก่อนยืนยันว่าเป็นผลทดลองของโครงงาน ค่า COCO จากแหล่งอ้างอิงต้องคงแยกจากผลใบหน้าและผลทั้งระบบ
3. บท 3 และบท 5 ยังระบุการประเมินทั้งระบบเป็นแผนงาน แม้ปกเปลี่ยนเป็นฉบับสมบูรณ์ตามตัวอย่างแล้ว สถานะของผลจริงต้องเขียนตรงตามที่มี ไม่เติมผลทดลองขึ้นใหม่จากการเปลี่ยนประเภทปก
4. ตารางข้อมูลหลักยังไม่แสดง PK/FK, cardinality, ชนิดข้อมูลและข้อจำกัด ขณะที่แผนภาพใช้ Database หลายจุด ควรพิจารณา ER Diagram และ Data Dictionary ให้ตรวจสอบความสัมพันธ์ได้ โดยตรวจความต้องการของอาจารย์ก่อนกำหนดว่าต้องมี Class Diagram แบบใด
5. สารบัญและตำแหน่งบทของตัวอย่างเพื่อนต่างจากรายงานนี้ ตัวอย่างเพื่อนไม่ทำให้โครงสร้างทั้งหมดเป็นข้อบังคับ ควรยึดคู่มือและข้อเสนอแนะอาจารย์ โดยเฉพาะผลเปรียบเทียบที่อาจารย์ให้ย้ายไปบท 4 แล้ว
6. ข้อความอธิบายพฤติกรรมระบบในภาพ เช่น อัตราเฟรมตัวอย่าง ชื่อ API, รูปแบบไฟล์ และการกลับมาใช้ Person ID เดิม ควรตรวจยืนยันกับระบบก่อนวาดภาพใหม่ การตรวจเอกสารรอบนี้ยังไม่ยืนยันรายละเอียดเหล่านั้น

## ลำดับที่แนะนำเมื่อได้รับอนุญาตให้แก้เนื้อหา

1. ยืนยันขอบเขตและชื่อโมเดลของแต่ละโหมด พร้อมสถานะงานที่ทำเสร็จจริง
2. ทำ Use Case และคำอธิบายสถานการณ์ให้ครอบคลุมโหมดไฟล์/ภาพนิ่ง/Livestream
3. แก้ Activity ที่ตรรกะผิดก่อน: Upload, Auto-Blur, Preview & Export
4. แก้ Activity ที่เหลือให้ใช้สัญลักษณ์สม่ำเสมอ แล้วปรับ Sequence ให้สอดคล้องกับสถานการณ์เดียวกัน
5. ตรวจความสอดคล้องกับตารางข้อมูล API และข้อความในบท 1, 4, 5 ก่อนจัดรูปแบบ PDF รอบใหม่
